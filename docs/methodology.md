# Methodology

> **Status:** student prototype on **synthetic data**. Nothing here has been validated on PepsiCo or any real operation.

## 1. Problem framing

For each product stored in a warehouse, on each day, predict whether it **will stock out within the next H days**. This is a binary classification task with an imbalanced positive class.

| Item | Definition |
|---|---|
| Unit of observation | one row = one product × one warehouse × one day (end-of-day snapshot) |
| Prediction horizon `H` | **7 days** by default (`HORIZON_DAYS` in `src/utilities.py`, configurable) |
| Target | `stockout_within_horizon` — 1 if `stockout_flag == 1` on **any** of days t+1 … t+H, else 0 |
| Unlabelled rows | last H days of each series have an unobserved future → label is `NaN` and they are excluded from training and testing |
| Primary model | `sklearn.tree.DecisionTreeClassifier` |

A *stockout* is a day on which demand exceeded available stock (sales were lost).

## 2. Target construction (`src/target_generation.py`)

1. Sort by product, warehouse, date.
2. For each k = 1…H, look k rows ahead **and confirm the date is exactly k calendar days later** (so gaps cannot produce wrong labels).
3. Label = 1 if any observed future day had a stockout; 0 if all H future days were observed with none; otherwise `NaN`.

Today's stockout flag is **not** part of the label (day t is excluded), so the label is genuinely about the future.

## 3. Feature selection (`src/feature_engineering.py`)

Rule: **a feature at date t may only use information from dates ≤ t**, because that is all a manager would have when the prediction is made.

Groups used: current stock and coverage, rolling demand level / variability / trend, lead time and reorder point, replenishment status (open order), stockout history, calendar, category and warehouse. See `feature_dictionary.md`.

Deliberately **excluded**:
* `product_id`, `product_name`, `date` — high-cardinality identifiers let a tree memorise individual products or periods.
* the target and anything derived from future rows.
* `replenishment_received` — available in the raw file for the simulator's own bookkeeping only; not used as a predictor.

`tests/test_features.py::test_features_do_not_use_the_future` enforces this: it scrambles all data after a cutoff date and asserts every feature on or before the cutoff is unchanged.

## 4. Why the label is not trivially predictable

The simulator (`src/data_generator.py`) produces stockouts from two sources the model cannot see in advance:
* **random supplier delays** (each series has its own delay probability), and
* **stale planning**: reorder points are computed from a fixed demand estimate, so they become too low during seasonal peaks, promotions and trend growth.

No column is derived from the label. A throw-away probe with a plain decision tree and a time-aware split gave an ROC-AUC of about 0.8 and precision of about 0.35 — clearly learnable, clearly not memorised. Formal numbers come from the evaluation module (`src/evaluate_model.py`), see section 8.

## 5. Validation design (implemented in `src/train_model.py`)

* **Time-aware split:** train on earlier dates, test on the latest ~20 % of dates.
* **Purge gap of H days** between train and test: a training row at date t has a label that peeks at t+1…t+H, so rows within H days of the cut-off would leak test-period outcomes into training.
* **Hyperparameter search:** `GridSearchCV` with `TimeSeriesSplit` (never shuffled K-fold), scored with recall/F-beta for the stockout class.
* **Class imbalance:** `class_weight="balanced"` as a tunable option.
* **Metrics:** recall for the stockout class is emphasised; accuracy alone is misleading because ~92 % of rows are low-risk.

## 6. Interpretability

Decision paths are read directly from the fitted tree (`decision_path`), and the text of each explanation is assembled from the thresholds actually crossed and the product's actual values. No generative model is involved. Feature importance describes what the *tree* used, not what *causes* stockouts.

## 7. Honest evidence levels

| Claim | Status |
|---|---|
| The pipeline runs end-to-end on synthetic data | demonstrable |
| Model metrics on the synthetic hold-out period | measured (section 8) |
| Performance on real distribution data | **not measured** |
| Business impact (fewer stockouts, saved sales) | **not measured** |

## 8. Measured results (synthetic hold-out, shipped model)

Source of truth: `models/training_report.json`, regenerated by `python -m src.train_model --tune`.

| | Train | Test |
|---|---|---|
| Period | 2025-01-28 → 2026-03-05 | 2026-03-13 → 2026-06-23 |
| Rows | 24,120 | 5,868 |
| Stockout-class share | 6.2 % | 16.8 % |

A 7-day purge gap separates the two periods.

| Method | Recall | Precision | F1 |
|---|---|---|---|
| Decision tree (depth 5, balanced, min leaf 100) | 86.4 % | 33.8 % | 0.486 |
| Rule "days of cover < lead time" | 80.1 % | 31.0 % | n/a |
| Always "Low Risk" | 0 % | n/a | 0 |

ROC-AUC 0.84, PR-AUC 0.46 (a random scorer's PR-AUC would be about 0.17).

How to read this:
* The tree catches roughly 6 more stockouts per 100 than the simple manager rule, with a similar false-alarm burden. It is a **modest** improvement, not a breakthrough.
* About 2 false alarms occur per real stockout caught. That cost is acceptable only if a check is cheap.
* Precision is lower than it would be in a calm period partly because the test period has a much higher stockout rate than training (distribution shift, see `limitations.md`).
* Hyper-parameter search (time-ordered CV, F2 score) changed hold-out F1 by only 0.003, so results are not sensitive to those settings.

### Risk score is not a calibrated probability
The "risk probability" is the share of the (class-weighted) training rows in a leaf that were stockouts. `evaluate_model.calibration_table` compares score against observed rate so the gap can be inspected.
Node "value" counts in the tree plot are likewise class-weighted, which is why the root looks perfectly balanced.
